## 1. 改动核心（v1 → v2）

| 改动 | 内容 |
|------|------|
| 调度 | 固定流水线 → **Agent Loop**（LLM 自主选工具，标准流程写入系统提示词） |
| 工具 | 3 个大工具 → **9 个细粒度**（生成/运行/诊断/修复四拆 + 读源码/搜项目/读产物） |
| 对话 | 新增：生成前对话提约束 · 结果追问（可读被测源码、沿依赖下钻）· 对话迭代测试；不做通用问答 |
| 协议/UI | WS v2（chat / tool_call / 心跳）；侧边栏改对话式消息流 |
| AST | tree-sitter 转正主力（JAR 降可选、正则兜底），依赖显式声明 |

**已定护栏（3 条，有异议现场提）**：
① 被测源码**只建议、不代改**（工具层无写权限）；
② 修改断言**双重确认**（先变更内容对照、再风险提示；工具层硬校验，缺标记拒绝执行）；
③ 自动修复只对编译错误/mock 配置类全自动（≤3 轮），遇断言类/疑似源码 bug **必须停下问用户**。

## 2. 议题一【投票】：技术栈（决策 A）

| | A1 全面 TypeScript | A2 Python + 兼容修复 |
|---|---|---|
| 跨平台 | 单运行时，复用 VSCode 内置 Node，**用户零安装** | 需用户装 Python 3.12；兼容层封装编码/进程/路径 |
| 成本 | **三个工具全部重写** | 增量整改，成本低 |
| 框架联动 | 解锁 Pi / Mastra / Agents SDK(TS) | PydanticAI / Agents SDK(Py) |

讨论：重写工时能否承受？团队 TS 能力？「零安装」是否硬性目标？
（注：用户机器仍需 JDK+Maven 跑目标项目测试，两案相同，只能探测+引导。）

> ✅ **决议：选 A1，技术栈全部改为 TypeScript。**
> 理由：TS 对 Mac / Windows 的兼容性好，能减少一整类跨平台兼容问题；插件与后端同栈。
> 连带影响：三个 Python 工具用 TS 重写；AST 解析在 java-parser（纯 JS）/ web-tree-sitter（WASM）中选定；运行时基线 Node 20。

## 3. 议题二【投票】：Agent 框架（决策 B）

| 候选 | 语言 | 一句话 |
|------|------|--------|
| B1 自研 loop | 两案均可 | 核心 300~500 行；完全可控；Provider 层已自持，增量成本其实低 |
| B2 Pi（pi.dev） | 仅 TS（绑 A1） | 极简 harness，OpenClaw 底层、社区热；但项目新 |
| B3 PydanticAI | 仅 Py（绑 A2） | Pydantic 官方出品，与我们 IR 模型同族 |
| B4 OpenAI Agents SDK | 两案均可 | 唯一两案通吃的现成框架 |

硬约束（一票否决）：LLM 调用必须过自持 Provider 层；工具用我们的 schema；流式事件驱动 UI；历史消息自管。
讨论：选现成也只用它的 loop——是否干脆自研？（"piagent" 经查最接近 Pi，如另有所指带链接来。）

> ✅ **决议：用现成框架，不自研；选型标准 = 简单、易上手。**
> 理由：组员对 Agent 框架不太熟悉，选简单的框架不单是为了快速搭建项目，也能让大家顺便学习。
> 与决策 A 联动：候选收敛为 TS 框架 —— **Pi（pi.dev）/ OpenAI Agents SDK（TS）/ Mastra**（PydanticAI 仅 Python 出局；自研出局）。
> 📌 **补充决议（会后讨论确定）**：选 **Vercel AI SDK**——TS 候选中概念最简单（`streamText + tools + stopWhen` 就是完整的工具循环）、多模型原生支持（OpenAI/Anthropic/DeepSeek）、教程基数最大便于学习。
> - 导师提到的 **mini-swe-agent**（约 100 行 Python、bash-only 范式）：模型直接执行 shell 命令，与决策 A（TS）和安全护栏（源码只读/断言双重确认）冲突，**不用作项目框架**；改为全组「agent 是什么」入门读物。
> - **预案**：若后续觉得太难 → 依次换 Mastra（更完整、自带记忆）→ 自研极简 loop（工具已按 zod 定义，切换成本集中在 runtime 层）。

## 4. 议题三【确认】：行为细节

- 依赖下钻默认 ≤2 层，够不够？
- 任务运行中收到 chat：排队（默认）还是允许打断？
- 双重确认交互：侧边栏按钮（推荐，防歧义）还是文本回复？

> ✅ **决议**：
> - 依赖下钻：默认 2 层，不够之后再加；
> - 任务运行中收到 chat 是否允许打断：不自行设计，**取决于所选框架是否支持，框架支持什么就用什么**；
> - 双重确认交互：用**侧边栏按钮**。

### 6.5 会后补充决议（第三轮：会话持久化提前，2026-10-23）

> 原快决项「对话记录存硬盘：本期不做」**推翻，提前实现**：
> 每个对话存为 `agent-server/data/sessions/<sessionId>.json` 一个文件（内存仍是运行态缓存；30 分钟不活跃只清缓存、不删文件，重访静默重载）；
