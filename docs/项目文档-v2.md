## 1. 项目定位

### 1.1 一句话定义

AgentUnitTest 是 VSCode 中的**单元测试生成垂直对话 Agent**：用户选中代码后，Agent 自主完成「理解代码 → 检测环境 → 生成测试 → 执行 → 诊断 → 修复」全流程；并且用户可以在**全程与 Agent 进行多轮自然语言对话**——生成前提出测试要求、生成后就结果追问、通过对话迭代改进测试。

### 1.2 v1 → v2 的定性变化

| 维度 | v1（现状） | v2（目标） |
|------|-----------|-----------|
| 产品形态 | 一次性 workflow：触发 → 固定流水线 → 出结果 → 结束 | 垂直对话 Agent：任务与对话统一在同一会话中 |
| 控制流 | LangGraph 图边硬编码工具顺序，LLM 只在 Tool2 内部被调用 | LLM 在 Agent Loop 中**自主决定**调用哪个工具；标准流程降级为系统提示词中的「推荐路径」 |
| 用户交互 | 只能等待结果 / 取消 | 生成前对话提需求、结果后追问、对话式迭代测试 |
| 会话记忆 | `messages` 字段存在但全程未使用，每次请求零上下文 | 真实对话历史 + 会话隔离 + TTL + 上下文压缩 |
| 平台支持 | Mac 为主，Windows 存在多处隐性坑（编码/进程/JAR 依赖） | Mac / Windows 双平台一等公民，CI 双平台矩阵验证 |
| 工具粒度 | `generate_and_run_tests` 单体工具 | 拆分为生成 / 执行 / 诊断 / 修复 + 只读项目上下文工具 |

### 1.3 设计原则

1. **跨平台优先（Cross-platform first）**：任何技术选型、任何依赖引入，必须同时在 macOS 与 Windows 上可开发、可运行、可分发；平台差异封装在统一的兼容层内，不允许散落在业务代码中。
2. **对话即界面（Conversation as UI）**：任务触发（右键生成）本质上是一条「带结构化上下文的预设对话消息」；生成、追问、迭代共用同一会话与同一消息历史。
3. **收敛点唯一（框架无关 / 模型无关）**：Agent Runtime 基于 Vercel AI SDK（决策 B，§4.2），但框架接触面只收敛在 `runtime/` 与 `llm/` 两处；模型接入统一走自持工厂（§3.6），业务代码不得直接 import 模型/框架包。这样后续若框架不合适需要更换（预案：Mastra 或自研极简 loop），只需改这两处，工具与协议不动。
4. **垂直且克制**：只做单元测试域。明确不做通用编程问答（见 1.4）；明确不修改用户的被测代码（发现疑似 bug 只报告，不代改）。
5. **接口契约先行**：IR 数据模型、WebSocket 协议、工具接口契约先冻结（里程碑 M1），实现可在契约下替换——这是对冲「技术栈/框架尚未定」风险的核心手段。

### 1.4 能力边界（垂直域定义）

**支持（本期必须实现）：**

| 能力 | 说明 | 示例 |
|------|------|------|
| 默认生成流程 | 选中代码 → 右键/侧边栏按钮 → Agent 自动跑完推荐路径并汇报结果 | 「Generate Unit Tests」 |
| 生成前对话 | 选中代码后先与 Agent 讨论测试需求与约束，Agent 携带约束进入生成 | 「用 Mockito mock 掉 DAO，只测异常分支」「覆盖率重点放在边界值」 |
| 结果追问（可下钻源码） | 就本次测试结果问答；Agent 先读产物（失败详情/诊断报告/测试源码），必要时读取被测源码，并可沿依赖链逐层下钻下一层源码定位根因；对源码问题**只给修改建议，绝不直接修改** | 「为什么第二个用例失败了」「这个断言是什么意思」「是我的代码有 bug 还是测试写错了」 |
| 对话迭代测试 | 用户以自然语言要求修改测试，Agent 修改后自动重跑并汇报；**其中修改断言必须走双重确认流程（§3.7），不得随意修改** | 「补充 null 输入的边界用例」「改用 AssertJ 断言」「删掉第三个用例再跑一遍」 |
| 任务取消 | 运行中任务可取消，会话保留 | 「cancel」按钮 |

**不支持（垂直边界，需优雅拒绝并引导回测试话题）：**

- ❌ 与当前测试任务无关的通用编程问答（如「帮我写个爬虫」）
- ❌ 直接修改被测源码：无论追问答疑还是修复建议环节，Agent **只建议、不动手**——给出怎么改、为什么这么改，实际修改由用户完成（工具权限层强制：任何工具都没有被测源码目录的写权限）
- ❌ 未经双重确认的断言修改：任何断言变更（无论用户对话发起，还是自动修复流程建议）都必须完成「变更内容 → 风险提示」两次确认（§3.7），不得随意修改断言
- ❌ 【P2 · 本期不做】VSCode 重启后的会话恢复（已确认本期不做、协议预留；本期会话仅存于后端进程内存 + TTL，见 §4.3）

## 2. 产品形态与交互设计

### 2.1 触发方式（与 v1 一致，保留两种）

1. **右键菜单**：选中代码 → `Generate Unit Tests` → 直接以默认指令触发 Agent（无二次确认）。
2. **侧边栏**：监听 `onDidChangeTextEditorSelection`，实时显示选中代码预览、「生成测试」按钮，**以及 v2 新增的对话输入框与消息流**。

### 2.2 侧边栏形态：从「四状态状态机」到「对话式 UI」

v1 的四状态（idle / prompt / loading / result）保留为**视觉框架**，但核心交互升级为消息流：

```
┌─────────────────────────────┐
│ Test Agent                  │
├─────────────────────────────┤
│ [选中代码预览卡片]            │  ← prompt 态：预览 + 「生成测试」按钮
│ Calculator.java · add()     │     + 对话输入框（可先聊再生成）
├─────────────────────────────┤
│ 消息流（v2 新增）：            │
│  🧑 用 Mockito mock DAO      │  ← 生成前对话
│  🤖 好的，我将为 add() 生成    │
│     mock DAO 的测试…         │
│  ┌─ 任务卡片 ──────────────┐ │
│  │ ✔ 分析代码  ✔ 检测环境    │ │  ← loading 态渲染为任务卡片
│  │ ✔ 生成测试  ▶ 运行测试    │ │     （tool_call 事件驱动）
│  │ 结果：3/5 通过  [查看详情]│ │  ← result 态内嵌在消息流中
│  └─────────────────────────┘ │
│  🧑 为什么第 4 个失败了？      │  ← 结果追问
│  🤖 因为 divide(a,0) 期望抛…  │
├─────────────────────────────┤
│ [输入消息…]          [发送]   │  ← 任何时刻可输入；任务运行中发送
│                     [取消]   │     则排队至任务结束（UI 提示）
└─────────────────────────────┘
```

交互规则：

- **消息流是主界面**：任务进度（tool_call 事件）、生成结果（result 卡片）、Agent 文本回复（token 流式 + 完整消息）全部按时间顺序渲染在消息流中。
- **任务运行中收到 chat 消息**：默认排队，任务结束后作为下一轮输入；UI 明确提示「将在当前任务结束后发送」。用户也可先点「取消」再对话。
- **会话生命周期**：侧边栏每个 VSCode 窗口持有一个 sessionId；「清空对话」按钮触发 `clear_memory`；后端 30 分钟滑动 TTL 过期后自动清理（前端收到过期错误时提示新建会话）。

### 2.3 三个典型交互场景

**场景 A：右键直接生成（默认路径，等价 v1 体验）**

```
用户选中 add()/divide() → 右键 Generate Unit Tests
Agent: [analyze_code] → [inspect_environment] → [generate_tests] → [run_tests]
       全部通过 → result 卡片「测试通过 ✓ 5/5」+ 测试源码入口
```

**场景 B：生成前对话**

```
用户选中代码，在侧边栏输入：「只测 divide，除零要抛 IllegalArgumentException，用 JUnit5 断言」
Agent: 复述理解并确认约束 → 用户点击「生成测试」（或直接说「开始吧」）
Agent: analyze_code → inspect_environment → generate_tests(携带约束) → run_tests → 汇报
```

**场景 C：失败追问（源码下钻）+ 断言修改（双重确认）+ 对话迭代**

```
result 卡片「3/5 通过，2 失败」
用户：「为什么 testDivideByZero 失败了？」
Agent: [read_artifact 失败详情] → [read_project_file 被测源码 divide()]
       →（不足以定位时）[read_project_file 沿依赖链下钻下一层源码，如 divide() 调用的 Validator]
       → 「测试期望抛 IllegalArgumentException，但被测代码返回了 0。
          结合 divide() 及其依赖 Validator 的源码看，问题可能出在缺少除零校验；
          诊断分类：SUSPECTED_SOURCE_BUG。
          对被测源码我只能给出修改建议、不会代改，建议：在 divide() 入口增加
          if (b == 0) throw new IllegalArgumentException(...)。
          如果你确认当前行为符合预期，也可以改测试断言。」
用户：「代码是对的，把断言改成期望返回 0」
Agent: 【确认 1/2 · 变更内容】「将修改 testDivideByZero 的断言：
       assertThrows(IllegalArgumentException, ...) → assertEquals(0, result)。确认执行吗？」
用户:「确认」
Agent: 【确认 2/2 · 风险提示】「再次提醒：本次失败的诊断分类为 SUSPECTED_SOURCE_BUG，
       修改断言可能掩盖被测代码的真实缺陷。仍确定要修改断言吗？」
用户：「确定」
Agent: [repair_tests（携带双重确认标记）] → [run_tests] → 「已修改并重跑：5/5 通过 ✓」
```

### 3.2 Agent Runtime 设计（v2 核心变化）

**（1）ReAct 式工具循环取代固定图**

- Agent Loop 的每一轮：LLM 基于「系统提示 + 消息历史 + 工具结果」决定下一步——继续调用工具，或输出面向用户的文本。
- v1 的固定顺序（Tool1 → Tool3 → Tool2…）**不再硬编码为图边**，而是写入系统提示词作为「推荐路径」；LLM 可以偏离（例如：对话迭代场景下跳过 analyze/inspect，直接 repair + re-run）。
- 护栏：单次任务最大工具调用轮数（默认 25，可配置）；连续同类失败（如 run_tests 连续 3 次编译错误）触发「停止并向用户求助」策略；修复-重跑循环上限（默认 3 次，沿用 v1 retry_policy 思路）；**修复循环中若诊断分类为 ASSERTION_ERROR 或 SUSPECTED_SOURCE_BUG，必须停止自动修复，报告用户并转入 §3.7 断言双重确认，严禁擅自改断言**；结果追问时的依赖下钻读取默认不超过 2 层（防上下文爆炸，可配置）。

**（2）任务与对话统一为消息**

- `run_task`（右键触发）= 一条预设用户消息（「请为选中代码生成单元测试并运行至通过」）+ 结构化上下文（code / filePath / workspaceRoot）注入会话。
- `chat`（输入框发送）= 普通用户消息，进入同一会话历史。
- 因此「生成前对话 → 生成 → 追问 → 迭代」天然共享上下文，无需 v1 那样的独立请求通道。

**（3）系统提示词骨架（人员4 负责细化）**

```
角色：你是 VSCode 中的单元测试专家 Agent，服务于 Java 项目（架构预留多语言）。
推荐路径：生成测试任务默认按 analyze_code → inspect_environment →
  generate_tests → run_tests 执行；失败时 diagnose_failures →
  （测试代码问题）repair_tests → 重跑，最多 3 轮。
对话规范：
  - 用户可在生成前提出约束（mock 策略/覆盖重点/断言风格），必须原样传递给 generate_tests。
  - 结果追问优先引用 read_artifact 的真实产物作答，禁止凭空编造失败原因；
    产物不足以解释失败时，用 read_project_file 读取被测源码；仍不足则沿
    CodeAnalysis 依赖链逐层下钻下一层源码（默认最多 2 层）后给出根因分析。
  - 对被测源码的问题只给修改建议（怎么改、为什么），绝不代替用户修改。
  - 修改断言必须执行 §3.7 双重确认流程；确认未完成前禁止调用 repair_tests 做断言级修改。
垂直边界：与单元测试无关的请求，礼貌拒绝并引导回测试话题。
安全规范：禁止修改被测源码文件；只允许写测试目录下的生成文件（沙箱约束由工具层强制）。
```

**（4）上下文管理（ContextManager）**

- 长产物不入对话历史全文：`CodeAnalysis`、测试源码、构建输出等以「摘要 + 产物 ID」形式进入消息历史，Agent 需要细节时通过 `read_artifact` 按需读取（v1 的 artifact_store 机制保留并升级）。
- 历史裁剪：滑动窗口 + 超限摘要压缩（保留最近 N 轮完整消息 + 更早轮次的摘要）。
- token 预算：每轮调用前估算，超限自动压缩，避免大项目上下文爆炸。

### 3.3 会话与记忆

| 项 | 设计 |
|----|------|
| 隔离粒度 | sessionId（每 VSCode 窗口一个），服务端按会话隔离消息历史与任务状态 |
| TTL | 30 分钟滑动过期（沿用 v1 SessionMemoryManager 语义），过期后服务端清理、前端提示新建 |
| 并发 | 每会话同一时刻至多一个运行中任务；新 `run_task` 抢占旧任务（沿用 v1 行为）；`chat` 在任务运行中排队 |
| 取消 | 协作式取消：任务上下文携带 cancel 信号，工具在安全点检查并快速退出、清理沙箱（沿用 v1 sandbox 的恢复语义） |
| 持久化 | 【P2 · 本期不做】消息历史落盘（SQLite 或 JSONL），支持 VSCode 重启后恢复会话；已确认本期不做，接口预留 `session_state` 快照消息 |

### 3.4 工具层设计（细粒度化）

v2 将 v1 的三个大工具重组为 **9 个细粒度工具**——这是让 LLM 具备自主调度能力的前提（单体工具内部流程 LLM 无法干预）：

| 工具 | 职责 | 关键输入 | 输出 IR | v1 对应 | 负责人 |
|------|------|---------|---------|---------|--------|
| `analyze_code` | AST/依赖分析（分层降级策略见 6.6） | code, filePath, workspaceRoot, recursive, maxDepth | `CodeAnalysis` | Tool1 | 人员1 |
| `read_project_file` | 只读读取项目内源文件（对话答疑用） | path（限 workspaceRoot 内） | 文件内容（截断保护） | 无（新增） | 人员1 |
| `search_project` | 按符号名/文本检索项目文件 | query, kind | 匹配列表 | 无（新增） | 人员1 |
| `inspect_environment` | 构建工具/测试框架/mock 库/JDK/项目结构检测 | filePath, workspaceRoot | `EnvironmentContext` | Tool3 | 人员3 |
| `generate_tests` | 调用 LLM 生成测试代码（接收用户约束） | CodeAnalysis, EnvironmentContext, 原始代码, user_constraints | `GeneratedTest` | Tool2 拆分 | 人员2 |
| `run_tests` | 沙箱写入 + Maven/Gradle 执行 + 结果解析 | GeneratedTest, EnvironmentContext | `TestResult` | Tool2 拆分 | 人员2 |
| `diagnose_failures` | 失败分类：测试代码错误 / 断言错误 / mock 配置 / 疑似被测代码 bug | TestResult | `Diagnosis` | Tool2 拆分 | 人员2 |
| `repair_tests` | 依据 Diagnosis 修复测试代码 | GeneratedTest, Diagnosis | `GeneratedTest` | Tool2 拆分 | 人员2 |
| `read_artifact` | 读取历史产物（测试源码/失败详情/诊断报告/构建日志） | artifactId | 产物内容 | artifact_store 升级 | 人员2 |

工具接口统一契约（框架无关）：

- 每个工具以 zod schema 声明参数（即 AI SDK tool 的原生格式），返回模型同样用 zod 校验；
- 全部异步（TS 原生 async/await；构建执行等阻塞 IO 用 child_process/worker 封装，不得阻塞事件循环）；
- 每个工具接受取消信号（cancellationToken / cancel_requested）；
- 工具异常必须转为结构化错误返回给 Agent Loop（`{ok: false, error}`），由 LLM 决定重试或求助用户，不允许静默崩溃整个会话；
- **权限分级（硬约束）**：read_project_file / search_project / read_artifact 只读；generate_tests / repair_tests 仅可写测试沙箱目录；**任何工具都没有被测源码的写权限**；repair_tests 的断言级修改必须携带 §3.7 双重确认标记，缺失即拒绝执行。

### 3.5 数据模型（IR，跨语言预留）

沿用 v1 已验证的 Pydantic 模型语义，用 **zod schema + TS 类型**重述（**字段语义与 v1 一一对应**，M1 冻结；zod schema 即工具参数校验与 AI SDK tool 定义的单一事实源）：

- `CodeAnalysis`：package / imports / defined_symbols / external_symbols / unresolved_symbols / methods / dependencies / **language**（多语言扩展位）/ parse_tier
- `EnvironmentContext`：language / java_version / build_tool / test_framework / mock_library / existing_test_patterns / project_root / test_directory / module_structure / package_style / assertion_style / ci_environment
- `TestResult`：status（success / test_code_error / test_failure）/ test_count / passed_count / failed_count / failure_details / compilation_error / failing_tests / stderr
- `GeneratedTest`：package_name / class_name / code / target_file_path
- `Diagnosis`（v2 新增正式模型）：failure_class（TEST_COMPILE_ERROR / ASSERTION_ERROR / MOCK_CONFIG / SUSPECTED_SOURCE_BUG / FLAKY / ENV_ERROR）/ evidence / suggested_action / confidence
- `SessionState`（替代 v1 `AgentState`）：session_id / messages（对话历史）/ task_context（code, filePath, workspaceRoot）/ artifacts（产物 ID → 路径映射）/ latest（code_analysis, env_context, test_result, generated_test, diagnosis 的最新引用）/ cancel 状态

多语言扩展方式：IR 顶层带 `language` 字段；按语言差异下沉到子模型（如 `java_version` 归入 `JavaEnvDetails`）；工具实现按 language 分派。本期仅实现 Java，Python 支持不在本期范围（v1 文档中的 pytest/unittest 描述废止）。

### 3.6 模型接入层：自持 llm/ 工厂（人员4）

决策 B 定为 Vercel AI SDK 后，v1 `BaseLLMProvider` 的「屏蔽厂商 SDK 差异」职责由 AI SDK 的**统一模型接口**（LanguageModel）承担，自持部分收敛为一个工厂模块：

- `llm/factory.ts`：`getModel(provider, model, { apiKey?, baseURL? })` → 返回 AI SDK 模型对象；这是**全项目唯一的模型出口**
- Provider 支持：`@ai-sdk/openai`（OpenAI 及 openai-compatible 协议，**DeepSeek 走此通道**）/ `@ai-sdk/anthropic`（Anthropic）
- 凭证校验（对应 v1 validate_credentials）：工厂提供 `validateModel()`，发最小请求验证 key/模型可用性，错误映射为统一错误格式推送前端
- 重试与超时：AI SDK 内建 maxRetries + 服务端统一超时策略
- 流式事件：stream 中的 text-delta / tool-call / finish 分片由 runtime 统一映射为 WS 协议 v2 的 token / tool_call / agent_message（§5.3），**其他模块不得直接消费 AI SDK 流对象**
- **约束**：业务代码（tools/、protocol/、server）禁止直接 import `@ai-sdk/*` provider 包，只能经工厂取模型——保持「收敛点唯一」，换框架时只动 llm/ 与 runtime/

### 3.7 断言修改双重确认机制（v2 安全护栏）

断言是测试的语义核心——随意修改断言等价于「让测试迁就错误的行为」，可能掩盖被测代码的真实缺陷。因此 v2 将断言修改列为高危操作：

**触发范围**：任何对 assert*/verify 类语句预期值的修改——无论由用户在对话中提出，还是由 Agent 在自动修复流程中依据诊断建议。

**双重确认流程（两步缺一不可）：**

1. **第一次确认 · 变更内容**：Agent 复述将要执行的确切变更（目标用例、修改前/修改后的断言对照），用户明确同意后才进入下一步；
2. **第二次确认 · 风险提示**：Agent 引用 diagnose_failures 的诊断分类给出风险警示（SUSPECTED_SOURCE_BUG / ASSERTION_ERROR 类必须明确提示「修改断言可能掩盖被测代码的真实缺陷」），用户再次明确同意后才执行。

**工具层硬校验（第二道防线）**：`repair_tests` 的断言级修改必须携带双重确认标记（服务端在会话历史中记录的两次确认事件 ID），缺失标记时工具直接拒绝执行——不单纯依赖提示词约束（提示词可能被对话绕过）。

**与自动修复流程的联动**：diagnose → repair → re-run 自动循环仅对 TEST_COMPILE_ERROR / MOCK_CONFIG / ENV_ERROR 等非断言类修复自动执行；诊断分类为 ASSERTION_ERROR 或 SUSPECTED_SOURCE_BUG 时必须停止自动循环，报告用户并转入双重确认（对应验收 §10.1 场景 5/6/7）。

**源码只建议不修改（同域护栏）**：对被测源码的问题，Agent 在任何环节都只输出修改建议（怎么改、为什么这么改），实际修改由用户完成；该约束由工具权限层强制——9 个工具均无被测源码目录的写权限（§3.4 权限分级）。

## 5. WebSocket 通信协议 v2

### 5.1 连接管理

- 端点：`ws://127.0.0.1:{port}/ws?instanceId={id}`（端口 8765 起自动探测，instanceId 防陈旧连接——两项机制沿用 v1）
- 新增**心跳**：客户端每 30s `ping`，服务端 `pong`；两次心跳丢失判定断线，前端自动重连并以 sessionId 续接会话
- 健康检查：`GET /health`（沿用 v1，增加 `version` 与 `agent_framework` 字段便于诊断）

### 5.2 客户端 → 服务端

| 消息 | 用途 | 关键字段 |
|------|------|---------|
| `run_task` | 发起测试生成任务（兼容期接受旧 `run_agent` 别名） | sessionId, code, filePath, workspaceRoot, provider, model, **instruction?**（生成前对话形成的附加约束） |
| `chat` | 自然语言对话消息 | sessionId, message, **queue?**（默认 true：任务运行中排队） |
| `cancel` | 取消当前任务（会话保留） | sessionId |
| `clear_memory` | 清空会话历史 | sessionId |

> 安全说明：v1 允许 WS 消息携带 apiKey（本机回环可用），v2 保留该能力但**禁止任何日志打印 key**，且默认优先使用后端环境变量（见《优化点汇总》6.1 的安全整改）。

### 5.3 服务端 → 客户端

| 消息 | 含义 | v1 对应 |
|------|------|--------|
| `token` | Agent 文本回复流式增量（含 turnId） | 保留 |
| `agent_message` | 一轮 Agent 回复完成（完整文本，供前端渲染历史） | **新增** |
| `tool_call` | 工具调用事件：`{tool, status: running/done/error, callId, summary?}` | 取代 `step`（前端把 tool_call 渲染为任务卡片步骤） |
| `test_code` | 生成/修复后的测试源码推送 | 保留 |
| `result` | 任务级结果：passed / testCount / message / 产物路径 / **diagnosis 摘要** | 保留+扩展 |
| `error` / `cancelled` | 错误 / 取消确认 | 保留 |
| `session_expired` | 会话 TTL 过期通知（前端提示新建会话） | **新增** |

### 5.4 典型事件流

**生成任务（场景 A）：**

```
→ run_task {code, filePath, workspaceRoot}
← tool_call   {tool: "analyze_code",        status: "running"}
← tool_call   {tool: "analyze_code",        status: "done"}
← tool_call   {tool: "inspect_environment", status: "running"} … done
← tool_call   {tool: "generate_tests",      status: "running"}
← token ×N    （生成说明流式输出）
← test_code   {testCode, filePath}
← tool_call   {tool: "run_tests",           status: "running"} … done
← result      {passed: false, testCount: 5, failed: 2, diagnosis: "…"}
← agent_message {text: "5 个用例中 2 个失败，主要原因是…你可以问我细节或要求修改"}
```

**结果追问（场景 C）：**

```
→ chat {message: "为什么 testDivideByZero 失败了？"}
← tool_call {tool: "read_artifact",     status: "running"} … done
← tool_call {tool: "read_project_file", status: "running"} … done   ← 被测源码（必要时沿依赖链继续下钻）
← token ×N → agent_message {text: "测试期望抛出 IllegalArgumentException，但…；建议在被测代码中…（只建议，不代改）"}
```

## 6. 跨平台兼容规范（强制标准，与决策 A 路线无关）

> 本章为**强制性工程规范**：A1（全面 TS）已定案，以下规范按 TS/Node 栈落地（进程/编码/路径等通用原则对任何运行时同样适用）；PR 不符合规范不予合并。规范落地的公共封装（兼容层）由人员3 负责。

### 6.1 进程管理规范

- 子进程一律以 **argv 数组**方式 spawn，禁止拼接 shell 字符串（杜绝 sh/cmd 差异与注入）；
- Windows 终止进程树使用 `taskkill /pid {pid} /T /F`（或等价库封装），Unix 使用进程组信号；**禁止假设 SIGTERM 语义跨平台一致**；
- 后端进程启动就绪判定：以 `GET /health` 轮询为准（沿用 v1），不解析 stdout 文案。

### 6.2 编码规范

- 全链路强制 UTF-8：Node/TS 全链路默认 UTF-8（v1 Python 时代 main.py 里 reconfigure stdout 的补丁式写法随重写废止）；
- 调用 Java 子进程（Maven/Gradle/JAR）一律带 `-Dfile.encoding=UTF-8`，管道流显式按 UTF-8 解码；
- 读写用户项目文件显式指定编码，禁止依赖系统默认编码（Windows 中文环境默认 GBK 是 v1 多个 bug 的根源）。

### 6.3 路径规范

- 一律使用平台路径库（`pathlib` / `node:path`），禁止手写 `/` 或 `\\` 拼接；
- 与前端交换文件位置统一用 **file URI 或相对 workspaceRoot 的 POSIX 风格相对路径**，展示层再做本地化；
- 注意大小写敏感性差异（macOS 默认不敏感、Linux 敏感）：文件查找结果以实际枚举为准，不假设大小写。

### 6.4 环境探测规范

统一由兼容层提供探测函数，业务代码不得自行散落判断：

| 探测项 | 平台差异点 |
|--------|-----------|
| Node 运行时（A1 已定） | 优先复用 VSCode 内置 Node（`ELECTRON_RUN_AS_NODE` / `process.execPath` 派生），回退探测系统 Node ≥ 20 |
| Maven/Gradle wrapper | `mvnw.cmd`/`gradlew.bat` vs `mvnw`/`gradlew`（v1 executor 已有正确处理，收编入兼容层） |
| JDK | `JAVA_HOME` 语义、`java` 是否在 PATH、Windows 注册表安装项 |
| 换行符 | 生成写入用户项目的文件遵循项目现状（探测 `.gitattributes`/既有文件），临时文件统一 LF |

### 6.5 仓库与 CI 规范

- `.gitattributes`：`* text=auto eol=lf`；`*.bat *.cmd text eol=crlf`；
- **CI 双平台矩阵（新增，强制）**：`windows-latest` + `macos-latest`（+ `ubuntu-latest` 可选）跑单测与 E2E 冒烟；任何 PR 双平台必须全绿；
- 运行时基线：**Node 20 LTS（单一基线）**；v1 的全部遗留（3.12/3.14 双 venv、双 requirements.txt 等）留在旧仓库 `AgentUnitTest-backend` ——v2 **新建仓库**开发，旧仓库按第 9 章在地基 MVP 跑顺后归档只读，新仓库无历史包袱；
- 依赖锁定：npm workspaces monorepo，单一 package-lock.json 入库（消除 v1 双清单漂移）；AI SDK 锁定大版本（见 §11 风险 2）。

### 6.6 Java 分析后端策略（AST 解析分层，v2 调整）

v1 文档宣称 Tier1（JavaParser + JavaSymbolSolver fat JAR）为主力，但**当前仓库中既无 JAR 也无 java_analyzer 源码**（证据见《优化点汇总》3.1），实际长期运行的是降级层。v2 调整如下：

| 层级 | v2 定位 | 依赖 |
|------|--------|------|
| 主力 | TS 侧解析：**java-parser（纯 JS，prettier-plugin-java 同款）或 web-tree-sitter（WASM）**，由人员1 在 M1 做二选一 PoC（解析质量对比）后冻结 | **显式声明在 package.json**（修复 v1 lazy import 且未声明的缺陷），纯 JS/WASM 零原生编译、零 JDK 要求 |
| 可选增强 | JavaParser + JavaSymbolSolver JAR（符号级解析） | 默认关闭；仅当用户显式配置 `JAVA_ANALYZER_JAR` 且 JDK 可用时启用；JAR 获取方式与构建脚本入库（若保留） |
| 兜底 | 正则解析 | 保留（TS 实现，零依赖，能力有限） |

> **说明**：运行 Maven/Gradle 测试本身需要目标机器有 JDK——这是「给 Java 项目生成并运行测试」的任务域固有前提，不属于技术栈缺陷；`inspect_environment` 负责探测并给出清晰的用户引导（缺 JDK 时前端提示安装，而非静默失败）。

### 6.7 双平台 Done 清单（每个功能合并前自查）

- [ ] 无 shell 字符串拼接的子进程调用
- [ ] 无硬编码路径分隔符 / 无依赖系统默认编码
- [ ] 进程终止在 Windows 上能杀掉整个进程树（Maven 派生的 java 进程不残留）
- [ ] 新增依赖在 win/mac 双平台可安装（有预编译产物，无需本地编译器）
- [ ] CI 双平台矩阵通过
- [ ] 手工冒烟：Mac 与 Windows 各跑一遍场景 A（右键生成 → 通过）

## 10. 验收标准

### 10.1 功能验收（E2E，Mac 与 Windows 双平台均须通过）

| # | 场景 | 通过标准 |
|---|------|---------|
| 1 | 右键生成，测试全通过 | result 卡片显示通过；测试源码可见；临时文件已清理/或按配置保留 |
| 2 | 生成 → 失败 → 自动诊断修复 → 重跑 | Agent 自主完成 diagnose→repair→re-run（≤3 轮），最终汇报；诊断分类为断言/源码类时应转入场景 7 行为 |
| 3 | 结果追问与源码下钻 | 提问失败原因，Agent 引用真实产物与被测源码作答（可沿依赖链下钻下一层，默认 ≤2 层）；对源码问题只给修复建议、不代改（人工核对与 failure_details/源码一致，无编造） |
| 4 | 对话迭代（非断言类修改） | 「补充 null 输入边界用例」→ 测试更新并重跑，结果推送 |
| 5 | 断言修改双重确认 | 要求修改断言：Agent 先后发起两次确认（变更内容对照 → 风险提示），均同意后才执行并重跑；任一步拒绝则断言保持不变 |
| 6 | 双重确认硬校验 | 绕过对话层直接构造无确认标记的 repair 调用（WS 脚本模拟），工具层拒绝执行 |
| 7 | 自动修复流程的断言边界 | 构造诊断分类为 ASSERTION_ERROR / SUSPECTED_SOURCE_BUG 的失败，验证自动循环停止、报告并转入双重确认，而非擅自改断言 |
| 8 | 生成前对话 | 先约定 mock 策略再生成，产出测试代码体现该约束 |
| 9 | 任务取消 | 运行中取消，进程树无残留（Windows 重点检查 java/mvn 残留），沙箱恢复原状 |
| 10 | 垂直边界 | 问无关问题被礼貌拒绝并引导回测试话题 |
| 11 | 会话生命周期 | TTL 过期收到 session_expired；clear_memory 后上下文确实清空 |

### 10.2 非功能验收

- 后端冷启动 ≤ 5s（不含模型调用）；WS 断线重连 ≤ 3s 恢复；
- 日志与 UI 中无任何明文 API Key；

- 单任务 token 用量可观测（日志记录每轮 prompt/completion tokens，为后续成本优化留数据）。

## 附录 A：v1 → v2 术语与接口对照

| v1 | v2 | 说明 |
|----|----|------|
| `AgentState`（TypedDict，LangGraph 状态） | `SessionState` | 增加 messages 真实使用、artifacts 引用、任务上下文 |
| `run_agent`（WS 消息） | `run_task`（兼容期保留旧名） | 语义从「跑固定流水线」变为「发起一次 Agent 任务」 |
| —（无对话入口） | `chat` / `agent_message` / `token(turnId)` | 对话能力载体 |
| `step`（WS 消息） | `tool_call` | 粒度从 3 个工具变为 9 个，含 callId 与摘要 |
| `generate_and_run_tests`（单体工具） | generate_tests / run_tests / diagnose_failures / repair_tests / read_artifact | 拆分以支持 Agent 自主调度与对话迭代 |
| LangGraph `StateGraph` 固定边 | 基于 Vercel AI SDK 的 Agent Loop（streamText + tools + stopWhen） | 控制流从代码移入提示词+LLM 决策 |
| `MemorySaver`（checkpoint，仅线程隔离） | SessionManager + ContextManager | 真实会话记忆与上下文压缩 |
| Tier1 JavaParser JAR「主力」 | java-parser / web-tree-sitter 主力（TS，M1 二选一），JAR 可选增强 | 与仓库现实对齐 |
| `BaseLLMProvider`（自研协议） | `llm/` 工厂（基于 AI SDK 统一模型接口） | 屏蔽厂商 SDK 差异的职责由 AI SDK 承担，自持部分收敛为工厂 |
