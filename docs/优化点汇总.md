## 1. 背景与动因

v1 实现了「选中代码 → 固定三步流水线 → 输出测试结果」的最小闭环，功能可演示，但存在三类根本性短板：

1. **平台兼容性**：技术栈中多处隐含「Mac 开发假设」，Windows 上存在编码、进程管理、环境依赖等多处不兼容隐患，且无 CI 验证，问题只能在组员机器上爆出来；
2. **框架价值倒挂**：引入 LangChain/LangGraph 却只用了「固定图编排」，没有获得任何 Agent 能力（LLM 不参与决策），反而承担了框架复杂度、版本漂移与调试黑盒成本；
3. **产品形态缺陷**：当前是 workflow 而非 agent——无对话入口、无会话记忆的实际使用、结果一次性输出后用户无法追问或迭代，与「智能测试助手」的目标相去甚远。

本次重构围绕以上三点展开，另附带审计中发现的一致性/安全/工程化问题（第 5~7 节）。

## 2. 优化点一：跨平台兼容重构

### 2.1 现状问题清单（代码审计证据）

| # | 问题 | 证据位置 | Mac/Win 影响 |
|---|------|---------|--------------|
| P1 | **JavaParser fat JAR 子进程（宣称的 Tier1 主力）在本仓库实际不可用**：`find_jar()` 搜索的是 `SoftwareTest/`、`backend1/java_analyzer/target` 等**遗留仓库布局路径**，当前仓库中既无 `java_analyzer` 源码目录也无任何 `.jar` 文件 | `backend/tools/ast_analyzer/javaparser_client.py` L34-67；全仓库 `find *.jar` 为空 | 双平台都跑不了 Tier1；且 JAR 路线本身要求每台机器 JDK + Maven 构建，是环境差异最大的组件 |
| P2 | **tree-sitter（Tier2）依赖未声明**：解析器内 lazy import `tree_sitter`/`tree_sitter_java`，但两份 requirements.txt 均无此依赖 → 未手动安装的环境会**静默降级到 Tier3 正则解析**，解析质量与文档宣称严重不符 | `backend/tools/ast_analyzer/treesitter_parser.py` L107-111；`requirements.txt` 全文无 tree-sitter | 双平台；典型的「文档说有、实际没有」 |
| P3 | **Windows 控制台编码坑已有补丁证据**：main.py 开头 `sys.stdout.reconfigure(encoding="utf-8")` 是典型的中文 Windows GBK 控制台补丁；子进程管道、文件读写仍有多处未显式指定编码 | `backend/main.py` L5-6 | Windows |
| P4 | **进程终止语义平台不一致**：BackendProcess 用 `kill('SIGTERM')`→3s 后 `kill('SIGKILL')`；Windows 上 Node 的信号是模拟语义，且 Maven 派生的 java 子进程树无法靠杀父进程回收 → 取消任务后可能残留孤儿进程 | `extension/src/back/BackendProcess.ts` L336-351 | Windows 为主 |
| P5 | **Python 环境探测的碎片化**：`python` vs `python3`、venv `bin/` vs `Scripts/` 各处双份硬编码；仓库内 `.venv312`（Python 3.12）与 `.venv`（Python 3.14）**双虚拟环境并存**，团队环境基线漂移 | `extension/src/back/BackendProcess.ts` L429-449；仓库根目录 | 双平台 |
| P6 | **Windows 构建 wrapper 已有特判**：executor 中 `cmd.exe /d /c mvnw.cmd` 的特判逻辑本身正确，但说明构建执行链路已实际踩过 Windows 坑，同类逻辑分散未收编 | `backend/tools/test_runner/executor.py` L92-100 | Windows |
| P7 | **无 CI**：仓库无任何 GitHub Actions/流水线配置，跨平台验证完全依赖组员手工 | 全仓库无 `.github/` | 双平台 |

### 2.2 优化目标

**Mac 与 Windows 上：开发体验一致、功能一致、可分发运行一致**；平台差异全部收敛到一个兼容层；每次提交经双平台 CI 验证。

### 2.3 方案要点（详见项目文档 v2 第 4.1 章 + 第 6 章）

**两条技术路线并列（✅ 决议 2026-10-17：选 A1 全面 TypeScript，A2 内容保留作为决策依据存档）：**

| | A1：全面转向 TypeScript/Node | A2：保留 Python + 系统性修复 |
|---|---|---|
| 核心思路 | Extension 与 Agent Server 同栈；可复用 VSCode 内置 Node 启动后端，**用户零环境安装**，P3/P4/P5 整类问题天然消失 | 保留现有工具资产；新建 `tools/platform/` 兼容层统一封装进程/编码/路径/环境探测；P1/P2 通过 AST 分层策略调整解决 |
| AST 方案 | `java-parser`（纯 JS）或 `web-tree-sitter`（WASM），零原生编译 | tree-sitter 依赖**显式声明**（官方 wheel 双平台齐备）；JAR 降为可选增强；正则兜底 |
| 成本 | 三个 Python 工具全部重写（成本高） | 增量整改（成本低） |
| 主要风险 | 重写回归缺陷 | 用户机器仍需 Python 3.12 环境；环境漂移需纪律约束 |
| 与框架决策联动 | 解锁 Pi / Mastra / Vercel AI SDK 等 TS 框架 | 对应 PydanticAI / OpenAI Agents SDK(Py) |

**无论选哪条路线，以下强制规范两案通用（项目文档 v2 第 6 章）：**

1. 进程管理：argv 数组 spawn、禁止 shell 字符串拼接；Windows 用 `taskkill /T /F` 杀进程树；就绪判定只看 `/health` 不解析 stdout；
2. 编码：全链路显式 UTF-8（Python 注入 `PYTHONUTF8=1`，取代 reconfigure 补丁）；
3. 路径：一律平台路径库；前后端交换用 file URI 或相对路径；
4. 环境探测：统一收编进兼容层（python/wrapper/JDK/换行符）；
5. 仓库：`.gitattributes` 统一 LF（bat/cmd 除外）；CI 双平台矩阵（windows-latest + macos-latest）；单一运行时基线（Node 20 LTS 或 Python 3.12，清理双 venv）；
6. 每个 PR 过「双平台 Done 清单」（项目文档 v2 §6.7）。

> **诚实说明**：目标 Java 项目的测试执行需要用户机器有 JDK + Maven/Gradle——这是任务域固有前提，不属于可消除的技术栈问题；v2 的处理方式是前置探测 + 明确的用户安装引导，而非静默失败。

## 3. 优化点二：替换 LangChain / LangGraph

### 3.1 现状问题清单（代码审计证据）

| # | 问题 | 证据位置 |
|---|------|---------|
| L1 | **框架能力与用法严重错配**：LangGraph 被用作 3 节点**固定线性流水线**（`analyze_code → inspect_env → run_tests → END`），无任何条件边、无 LLM 决策节点——付出了框架学习与复杂度成本，没有获得任何 Agent 能力 | `backend/agent/graph.py` L104-112 |
| L2 | **「伪对话」状态**：`AgentState.messages` 用 `add_messages` 注解声明了对话历史，但全流程没有任何代码读写它；MemorySaver checkpoint 只起到 thread_id 隔离作用，从未用于对话恢复 | `backend/agent/state.py` L16；graph.py 全文 |
| L3 | **进度推送深度耦合框架内部事件**：main.py 用 `astream_events(version="v2")` 监听 `on_chain_start`/`on_chain_end`/`on_chat_model_stream` 等 LangChain 内部事件名驱动 WS 推送——框架升级即碎，且事件语义是「猜」出来的黑盒 | `backend/main.py` L214-281 |
| L4 | **版本漂移**：v1 文档宣称 langchain 1.2.x / langgraph 1.1.4 + tree-sitter 0.25.x + websockets 15.0.1；实际锁定 langchain==1.0.3 / langgraph==1.0.5，tree-sitter 与 websockets 根本不在依赖清单中 | v1 文档 vs `backend/requirements.txt` |
| L5 | **框架开销**：社区实测 LangGraph 每步有可观的 token 开销与延迟（见参考资料），对我们要做的多轮对话 Agent 会放大成本 | 外部实测（附录） |

### 3.2 优化目标

用**真正提供 Agent 能力**（LLM 自主工具调度、多轮对话、流式事件）且**复杂度与收益匹配**的运行时替换 LangChain/LangGraph；同时保证替换动作本身不绑架其他模块（Provider 层、工具层、协议层与框架解耦）。

### 3.3 方案要点（详见项目文档 v2 §4.2）

候选对比（完整版含风险与依赖关系见项目文档）：

| 候选 | 语言 | 一句话评价 |
|------|------|-----------|
| **B1 自研轻量 Agent Loop** | 两案均可 | 核心约 300~500 行；我们已自持 Provider 抽象，自研增量只有 loop+调度+上下文管理；完全可控、教学价值高；需自行打磨流式/重试/压缩 |
| **B2 Pi（pi.dev）** | 仅 TS（绑定 A1） | 极简 harness，`pi-ai` + `pi-agent-core` 分层与我们的 Provider 理念一致；OpenClaw 底层、社区热度高；但项目新、API 可能变动。注：搜索确认「piagent」大概率即指此框架，未发现同名的其他主流框架 |
| **B3 PydanticAI** | 仅 Python（绑定 A2） | Pydantic 官方出品，与我们 IR 模型同族，类型安全与结构化输出最佳 |
| **B4 OpenAI Agents SDK** | Python/TS 双版本 | 唯一两案都可用的现成框架；handoff/guardrail/session 原语齐全；接非 OpenAI 模型需经兼容适配（Provider 层可解决） |
| **B5 Vercel AI SDK ✅ 选定（会后正式列入候选）** | 仅 TS（绑定 A1） | 概念最简单：`streamText + tools + stopWhen` 即完整工具循环；多模型原生支持（OpenAI/Anthropic/DeepSeek）；流式事件与侧边栏协议一一对应；TS 生态教程基数最大、便于学习 |
| B6 其他 | — | **Mastra**（TS，更完整：自带记忆/workflow/Playground，定位为**第一备选**）；Microsoft Agent Framework（过重）；smolagents（code-agent 范式不合）；mini-swe-agent（Python + bash-only 范式，与决策 A 及安全护栏冲突，转为全组入门读物）——未选，理由留档 |

**四条硬约束（无论选谁）：** LLM 调用必须过自持 `BaseLLMProvider`；工具以我们的 schema 注册、不接受侵入式基类；流式事件必须足以驱动 UI；消息历史由我们管理。
**决策机制：** M0 选型会按「语言匹配（一票否决）→ 硬约束（一票否决）→ 学习成本/社区/能力打分」投票；自研与现成不互斥——选现成框架也只用其 loop，其余自持。

> ✅ **决议（2026-10-17 选型会定方向 + 会后讨论定框架）**：方向为**用现成框架（不自研）**，标准 = 简单易学；最终选定 **Vercel AI SDK**。Pi 评估后认为对现阶段团队偏难，排除；导师提到的 **mini-swe-agent** 经评估为 Python + bash-only 范式（模型直接执行 shell 命令），与决策 A 及「源码只读/断言双重确认」安全护栏冲突，不用作项目框架，改为全组「agent 是什么」入门读物（约 100 行源码）。第一备选 Mastra，兜底自研极简 loop（切换成本集中在 runtime 层）。硬约束 1 相应调整：模型接入收敛在自持 llm/ 工厂（基于 AI SDK 统一模型接口），详见项目文档 v2 §3.6。

## 4. 优化点三：Workflow → 垂直对话 Agent

### 4.1 现状差距

| 差距 | v1 现状 | 证据 |
|------|--------|------|
| 无对话入口 | WS 协议只有 `run_agent`/`cancel`/`clear_memory`，用户无法发送自然语言 | `backend/main.py` L92-128 |
| 无自主决策 | 工具顺序硬编码为图边；LLM 仅在 Tool2 内部被当作「测试代码生成器」调用，不参与任何调度决策 | `backend/agent/graph.py` |
| 无记忆利用 | messages 字段空置；每次请求零上下文，上一次生成的结果对下一次请求不可见 | `backend/agent/state.py` L16 |
| 结果一次性 | result 推送后交互终结：无法追问失败原因，无法要求修改重跑 | 协议与 UI 均无后续通道 |
| UI 非对话式 | 侧边栏为四状态状态机（idle/prompt/loading/result），无消息流、无输入框 | v1 文档 §侧边栏 |

### 4.2 目标能力（已与需求方确认边界）

| 能力 | 是否支持 | 说明 |
|------|---------|------|
| 默认生成流程（右键/按钮触发） | ✅ | 保持 v1 体验，内部改为 Agent 按推荐路径执行 |
| 结果追问（可下钻源码） | ✅ | 「为什么失败/是不是被测代码有 bug」；Agent 读取真实产物作答，禁止编造；必要时读取被测源码并沿依赖链下钻下一层（默认 ≤2 层）定位根因；对源码问题**只给修改建议，不代改** |
| 生成前对话 | ✅ | 选中代码后先约定约束（mock 策略/覆盖重点/断言风格），Agent 携带约束生成 |
| 对话迭代测试 | ✅ | 「补充边界用例/改用 Mockito/删掉某用例重跑」→ Agent 修改测试并自动重跑；**修改断言必须双重确认**（先确认变更内容对照、再确认风险提示；repair_tests 工具层硬校验，缺确认标记拒绝执行） |
| 通用编程问答 | ❌ | 垂直边界：礼貌拒绝并引导回测试话题 |
| 修改被测源码 | ❌ | 只写测试目录（沙箱强制）；任何工具无被测源码写权限；发现疑似 bug 仅报告并给修改建议，由用户动手 |
| 未经确认的断言修改 | ❌ | 任何断言变更（含自动修复流程建议的）都必须走双重确认；诊断为 ASSERTION_ERROR / SUSPECTED_SOURCE_BUG 时自动修复循环必须停下询问用户 |

### 4.3 架构改动清单（详见项目文档 v2 §3）

| 层 | v1 | v2 |
|----|----|----|
| 调度 | LangGraph 固定边 | **ReAct 式 Agent Loop**：LLM 自主决定工具调用；标准流程写入系统提示词作「推荐路径」；护栏：轮数上限、修复-重跑 ≤3 次、连续失败求助用户、**断言类修复必须停止自动循环走双重确认（变更内容→风险提示）+ 工具层硬校验**、依赖下钻 ≤2 层 |
| 工具粒度 | 3 个大工具（Tool2 为 generate+run+diagnose+repair 单体） | **9 个细粒度工具**：analyze_code / inspect_environment / generate_tests / run_tests / diagnose_failures / repair_tests / read_project_file / search_project / read_artifact —— 拆分是对话迭代（只 repair+重跑）与答疑（按需读产物/源码）的前提 |
| 状态 | `AgentState`（任务字段 + 空置 messages） | `SessionState`：真实消息历史 + 任务上下文 + 产物引用；长产物「摘要+ID」化，细节经 read_artifact 按需读取（防上下文爆炸） |
| 协议 | run_agent / step / result | **协议 v2**：新增 `chat`、`agent_message`、`tool_call`（取代 step）、`session_expired`、心跳；`run_task` 兼容旧 `run_agent`（项目文档 v2 §5） |
| 记忆 | SessionMemoryManager 仅 TTL 元数据 + MemorySaver 隔离 | 会话历史真实管理：隔离 + 30min 滑动 TTL + 滑动窗口/摘要压缩 + token 预算 |
| UI | 四状态状态机 | **对话式消息流**：任务进度渲染为内嵌卡片，任何时刻可输入；任务运行中 chat 排队（项目文档 v2 §2.2） |
| 触发语义 | run_agent = 跑流水线 | run_task = 一条预设用户消息 + 结构化上下文 →「生成」与「对话」统一为消息 |
